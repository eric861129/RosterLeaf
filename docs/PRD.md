## 1. 產品定位與設計原則

### 1.1 定位

RosterLeaf 是「以 Excel 為資料交換方式的視覺化排班工作台」，不是需要註冊的 HR SaaS，也不是派遣、打卡、薪資或請假簽核系統。

主要使用者是負責安排小型或中型團隊班表的店長、行政、值班負責人與活動人力協調者。首版以 5–100 名人員、單次 1–31 天的排班區間為設計及驗收範圍；同一專案可以保留其他日期資料，以支援跨週檢查。

單一班表專案由一名操作人員在本機編輯。檔案可交給其他人接續操作，但首版不提供多人同時編輯、登入或雲端同步。

### 1.2 要解決的問題

目前構想聚焦四項待驗證的使用者問題：人員可排時段散落於不同檔案、臨時調班需要大量複製貼上、時間衝突及人力缺口難以直接看見，以及匯出漂亮班表後無法保留完整規則繼續編輯。

產品價值不是增加更多管理欄位，而是減少從「人員資料」到「可交付班表」之間的操作。

### 1.3 核心原則

1. **Excel 往返可靠。** 可再次匯入的完整專案檔與供閱讀的班表檔分開。
2. **人工保有控制。** 自動排班先提供預覽；不直接覆寫既有安排。
3. **限制透明。** 不可排就是不可排；排不滿須顯示缺口，不能偷偷放寬限制。
4. **本機處理為預設。** 不主動將名單、規則或班表傳送到伺服器。
5. **操作不只靠拖拉。** 拖拉、點選表單及鍵盤均能完成核心編輯。
6. **先完成閉環。** 先把匯入、排班、調整、檢查、匯出及再匯入做好，再擴充 HR 功能。

### 1.4 方案取捨

| 方向 | 優點 | 代價 | 決定 |
| --- | --- | --- | --- |
| 僅提供手動拖拉與 Excel | 產品及工程範圍較小 | 無法完整回應快速產生班表的需求 | 作為第一個開發切片，不是最終 MVP |
| 本機規則式自動排班＋手動調整 | 保留靜態部署、免帳號與資料本機處理 | 無法承諾全域最佳解，需要缺口及解釋介面 | 首版採用 |
| 雲端 AI／大型最佳化服務 | 可延伸複雜求解與跨人員協作 | 增加後端、資料傳輸、費用及維護 | 首版不採用 |

## 3. 使用者故事與主要流程

### 3.1 使用者故事

- 身為排班人員，我能直接匯入既有的人員資料，對應姓名與人員編號，不需逐人新增。
- 身為排班人員，我能設定每週及特定日期的可排／不可排時段，避免誤排。
- 身為排班人員，我能說明每個時段需要幾位、具備什麼職務的人，系統才有依據產生草稿。
- 身為排班人員，我能保留已確認的班次，只補上空缺；也能查看重新安排未鎖定班次的變更預覽。
- 身為排班人員，我能用拖拉或表單修改班表，立即知道是否衝突、是否出現缺額。
- 身為排班人員，我能把完整專案存成 Excel，下次或換電腦後繼續使用。

### 3.2 第一次使用

開啟網站 → 選擇「使用範例」或「建立專案」→ 設定名稱、日期區間與時區 → 匯入人員及可排時段 → 建立班次範本與需求 → 手動排班或產生草稿 → 調整並處理警示 → 匯出班表及專案檔。

不要求使用者一開始填完所有設定。可先使用範例體驗，也可先建立手動班表；只有執行自動排班時，才必須有明確的人力需求。

### 3.3 再次使用

開啟最近專案或匯入專案 Excel → 切換／新增排班日期區間 → 選擇性匯入更新的人員或時段 → 確認新增、修改及影響 → 產生與調整班表 → 再次匯出。

### 3.4 交接給另一個人

匯出完整專案 Excel → 透過使用者自行選擇的方式傳送 → 對方匯入後接續操作。此流程是檔案交接，不是即時共編；專案 ID、版本與匯出時間需可見，避免誤用舊版。

## 4. 資訊架構與介面

### 4.1 主要工作區

產品主體採三個功能頁籤：「排班」、「人員與時段」、「班次與需求」。專案管理位於進入畫面或切換面板；匯入、匯出、規則及說明透過獨立面板開啟，避免主導覽膨脹。

### 4.2 排班工作台

上方提供專案名稱、日期切換、週／日視圖、搜尋及篩選、自動排班、Undo／Redo、檢查與匯出。主要區域呈現班表；側邊呈現未排需求、候選人及當前選取項目的資訊。底部或摘要列顯示人力缺口、限制違反與排定時數。

篩選只改變畫面，不得偷偷改變自動排班或匯出範圍；需要限定操作範圍時，必須明示「只處理目前篩選的人員／日期」。

### 4.3 週班表

以人員為列、日期為欄，每格呈現一張或多張班次卡片。適合檢視每人本週安排、跨日期移動、跨人員改派與複製班次。週視圖不以拖拉卡片邊緣調整分鐘；精細調整在單日時軸或編輯面板完成。

### 4.4 單日時軸

以人員為列、時間為橫軸，班次呈現可移動及縮放的時間區塊。可排、不可排及已排狀態須有文字或圖示輔助，不能只靠顏色判斷。跨日班在兩天視圖中呈現延續標記，但仍為同一筆指派，不得重複計數。

### 4.5 小螢幕與無障礙

手機首版以人員／日期篩選、班次列表與點選編輯面板為主，不承諾與桌面相同密度的時軸拖拉。保留瀏覽器滑動，不用整頁攔截滑動手勢。平板拖拉與捲動需有明確操作把手。

所有核心拖拉功能，均須能透過點選選單／表單完成，另提供鍵盤焦點、可讀標籤及鍵盤操作。這也符合 W3C 對拖拉動作應有不需拖拉的單一指標操作替代方式之要求。[S5]

## 5. 人員、可排時段與資格

### 5.1 人員欄位

| 欄位 | 要求 | 說明 |
| --- | --- | --- |
| employee_id | 必填，專案內唯一 | 以文字處理；保留前導零；姓名不能當作識別鍵 |
| name | 必填 | 同名人員可存在 |
| roles | 選填 | 可勝任職務代碼；未設定時使用 GENERAL |
| department | 選填 | 搜尋與篩選，不是權限界線 |
| active | 必填，有預設 | 停用者不再接受新指派；既有資料保留並重新檢查 |
| availability_mode | 必填，有預設 | restricted 或 anytime；預設 restricted |
| target_weekly_hours | 選填 | 正數；用於偏好分配，不是保證工時 |
| max_daily_hours | 選填 | 設定後視為硬性上限；空白代表未啟用 |
| max_weekly_hours | 選填 | 設定後視為硬性上限；空白代表未啟用 |
| note / color | 選填 | 顯示輔助；不可影響排班資格 |

人員被班表引用時，預設只允許停用，不直接刪除。若確實需要刪除，須先處理關聯指派，顯示影響，並以同一筆交易執行。

### 5.2 時段表示

每筆時段有獨立 ID，包含 employee_id、scope、weekday 或 date、start_time、end_time、end_day_offset 與 type。

scope 為 weekly 或 date。weekly 使用 1–7 表示星期一至日；date 使用 YYYY-MM-DD。二者不得同時填入。type 為 available、unavailable、preferred。每人同一天可有多筆時段，不能用一個含糊的文字欄位儲存多個時間範圍。

### 5.3 可排判定

對 restricted 人員，可排基礎是「每週 available 區間與指定日期 available 區間的聯集」。對 anytime 人員，可排基礎是專案涵蓋的全部時間。接著扣除所有適用的 unavailable 區間。preferred 僅影響分配偏好，不增加可排資格。

因此，不可排時段永遠優先；指定日期的 available 不會偷偷覆蓋既有 unavailable。若使用者要允許例外，須修改或移除原本的不可排規則，介面要說明這個原因。

restricted 人員沒有任何可排資料時，不參與自動排班。匯入只有姓名的表格時，提供明確選項「將未設定時段的人員設為 anytime」，由使用者確認後套用，不可默認所有人隨時都能工作。

班次整個區間都必須被可排集合涵蓋，不能只檢查開始時間。

## 6. 班次範本與人力需求

### 6.1 班次範本

範本包含 template_id、名稱、起訖時間、跨日設定、預設職務及場地。使用者可將範本套用至指定日期或每週特定星期，產生可獨立編輯的需求資料。

已產生的需求是當時範本的快照；修改範本不能無聲改動現有班表，須另行選擇批次更新並預覽影響。

### 6.2 人力需求

每筆需求包含 demand_id、date、start_time、end_time、end_day_offset、role、location、required_count 與 note。required_count 為正整數。未設定職務或場地時，分別使用 GENERAL 及 DEFAULT。

例如：2026-10-05，09:00–13:00，櫃台，A 店，2 人。

同一場地及職務的重疊需求，首版要求先合併或切成不重疊的時間段，再進行自動排班，避免誤把重複輸入算成兩倍需求。不同職務的同期需求可以同時存在。

### 6.3 手動班表與需求的關係

手動班次可以不關聯需求，但會標示「未對應需求」。只有明確對應到 demand_id 且職務、場地相符的指派，才計入該需求的覆蓋。一筆指派最多對應一筆需求，不能在同一時間被算成兩種人力。

移動到其他日期或改變職務／場地時，必須重新選擇符合條件的需求或解除關聯；不能保留錯誤對應。與需求解除關聯可能使原需求出現缺口，須立即顯示。

### 6.4 休息與時數界線

首版的「排定時數」為實際被排入的時間區間長度，不等同打卡工時或薪資計算工時。首版不提供只有總休息分鐘卻沒有時間位置的隱性扣除，也不把分段班次之間的空白自動當成已符合班間休息規範。

若某段休息不應計為可服務人力，使用者須將班次拆成休息前後兩個區間。系統的需求覆蓋及時數只依這些明確區間計算。帶薪／不帶薪休息與實際出勤核薪不在首版範圍。

## 7. Excel 資料契約

### 7.1 檔案種類

**資料範本**用於初次填寫人員、時段、班次及需求，可只匯入此次需要的資料表。

**完整專案 Excel**用於備份、跨電腦交接及重新編輯，保留全部核心資料與規則。

**閱讀版 Excel**用於分發與列印，提供人員×日期班表、班次明細及排定時數摘要；預設不包含所有可排／不可排資料與內部備註。閱讀版清楚標示不是完整專案備份，不承諾可直接還原。

### 7.2 完整專案工作表

| 工作表 | 核心內容 |
| --- | --- |
| 說明 Instructions | 檔案用途、欄位說明、範例、狀態說明及注意事項 |
| 人員 People | employee_id、name、roles、department、active、availability_mode、工時設定 |
| 可排時段 Availability | availability_id、employee_id、scope、weekday／date、起訖時間、跨日、type |
| 班次範本 ShiftTemplates | template_id、name、起訖時間、跨日、role、location |
| 人力需求 Demands | demand_id、date、起訖時間、跨日、role、location、required_count |
| 班表資料 Assignments | assignment_id、employee_id、起訖日期時間、role、location、demand_id、locked、source、note |
| 設定 Settings | schema_version、project_id、project_revision、專案名稱、時區、選取區間、週起始日、排班規則及演算法設定 |

系統欄位名稱保持穩定，表頭附繁體中文說明或提供欄位對應。資料工作表一列一筆、不可合併儲存格；說明頁和閱讀版可以使用排版與格式。

資料契約不依賴底色、合併儲存格、隱藏欄位或 Excel 巨集。職務代碼採專案內一致的字串，People 多職務用分號分隔；代碼本身不得包含分號。第一版不另建立職務主檔或職能證照效期管理。

### 7.3 首版格式支援

首版支援 .xlsx 標準資料表及一般具表頭的名單欄位對應，不支援 .xls、.xlsm、加密活頁簿、PDF、圖片或任意人員×日期排版的班表自動還原。

標準範本中的日期及時間輸出為明確文字：日期 YYYY-MM-DD、時間 HH:mm、日期時間 YYYY-MM-DDTHH:mm。亦可接受真正具日期／時間型別的 Excel 儲存格，但須依活頁簿日期系統正確解讀。03/04/2026 等歧義文字不可自行猜測。

人員及記錄 ID 一律當成文字，不把 0012 轉為 12。空白列可忽略；空白必填欄位不能忽略。資料區的合併儲存格、公式與不支援型別需提示位置與修正方法。

首版不執行也不信任匯入公式的計算結果；需匯入的公式欄位請先在原檔貼上為值。匯出使用者輸入的文字時明確寫入文字型別，不把 =、+、-、@ 等開頭的內容變成公式。

### 7.4 匯入流程與錯誤

選擇檔案 → 辨識用途與 schema → 選擇工作表及欄位對應 → 格式／關聯驗證 → 顯示資料與衝突預覽 → 顯示新增、修改、保留數量 → 確認 → 原子提交。

錯誤至少包含工作表、列號、欄位、原因與修正建議。例如：「可排時段第 8 列，employee_id=E099 找不到對應人員。」

格式錯誤、重複 ID、無法解析時間與失效關聯會阻擋提交。匯入既有班表時發現的排班規則衝突則可以在明確確認後以草稿保存，但必須保留警示、不能標成完成檢查。

匯入取消或格式驗證失敗時，專案完全不變。首版不默認跳過錯誤列；需修正後重試。

### 7.5 更新、取代與版本

部分資料更新按穩定 ID 進行新增或更新，沒有出現在此次檔案中的資料保留，不代表刪除。同一份含穩定 ID 的檔案重複匯入，不得產生重複資料。

首次人員匯入若沒有編號，使用者可在預覽中明確選擇產生編號；接著應保存系統匯出的標準檔。沒有穩定 ID 的原始名單再次匯入時，不承諾自動辨識是更新，不以姓名直接合併。

完整專案匯入提供「另開專案」與「取代目前專案」；取代需顯示版本差異並先保留恢復快照。首版不自動合併兩份已分別編輯的完整班表。

schema_version 與專案內容版本 project_revision 分開。舊 schema 只能經明確支援的轉換遷移；遇到較新且不支援的 schema，阻止覆寫並提示升級。原始檔案不可被瀏覽器匯入流程修改。

### 7.6 Excel 往返驗收

專案匯出 → 在新的空白工作區匯入 → 比對標準化後的人員、時段、需求、指派、鎖定及規則，應完全一致。排序、匯出時間、派生檢查結果與檔案二進位內容不列為相等條件。

驗收同時涵蓋跨日班、同名人員、前導零 ID、空白選填欄位、多筆時段及跨週記錄。初版以指定版本的 Microsoft Excel 實際開啟、編輯、儲存後再匯入作為相容性測試；其他試算表軟體只有完成測試後才列入支援清單。

## 8. 排班編輯行為

| 操作 | 預期行為 |
| --- | --- |
| 點選空白格 | 新增班次，預填人員與日期 |
| 拖拉班次至其他人員 | 改派人員，保留原本時間，立即驗證資格及衝突 |
| 週視圖跨日期拖拉 | 變更日期，保留當地時間與時長，重新處理需求關聯 |
| 單日時軸水平拖拉 | 整段平移，保留時長 |
| 單日時軸拖拉左右邊界 | 調整開始或結束時間，不能小於等於零 |
| 點選班次 | 開啟編輯面板，精確輸入日期、時間、人員、職務及需求 |
| 複製班次 | 產生新的 assignment_id，原班次不變 |
| 鎖定／解鎖 | 鎖定者不能被拖拉、刪除或自動重排；須先明確解鎖 |
| 清除指派 | 刪除選定的指派而非需求，需求缺口即時更新 |
| Undo／Redo | 一次拖拉、批次套用或自動排班套用均視為一個操作 |

時間吸附預設 30 分鐘，可切換 15／30／60 分鐘；資料儲存保留分鐘精度。匯入非吸附格的 09:20 不可自行改為 09:30。拖拉預覽須顯示最終吸附值；表單允許精確到分鐘。

拖拉過程先顯示影子與預覽。放開後才提交；違反硬限制時回復原位置，顯示具體原因，而非留下一個無效狀態。軟偏好違反可以提交，但保留提示。批次操作若有任一硬限制違反，首版整批不套用，不偷偷只成功一部分。

## 9. 規則、衝突與需求覆蓋

### 9.1 永遠適用的限制

時間需有效且結束晚於開始；人員須存在且可接受新班次；同人不能有重疊指派；完整班次需在可排集合內；必須具備需求職務；已鎖定指派不能直接被變更。

### 9.2 使用者啟用後適用的硬限制

每人每日及每週排定時數上限，以及最多連續排班日數。這些設定預設留空／關閉，不套用任何未經確認的法定數字。

首版尚未建模「同一次勤務內休息」與「兩次勤務之間休息」的差異，因此不將最短班間休息列為已支援的硬限制；這項功能須與完整勤務／休息模型一同加入第二階段。不同場地之間的移動時間也不自動推算，需由使用者人工檢查。

規則變更前顯示受影響指派。既有或已鎖定班次若因此違反規則，保留為待處理草稿；鎖定不代表可略過規則。自動排班前須先處理這類硬衝突，不可把它們當成合格固定輸入。

### 9.3 軟偏好

優先安排偏好時段、盡量接近每人的目標工時，以及在可比較的資格／可排條件下均衡分配。不能只追求每人班次數一樣，忽略兼職與全職的可排差異。

目標工時不是最低保證，偏好也不是可排時段。首版不把年資、性別或其他與排班資格無關的個人特徵當成演算法分配依據。

### 9.4 時段與跨期計算

區間採 [start, end) 語意。09:00–12:00 與 12:00–15:00 不重疊；但沒有重疊不代表已檢查班間休息或交通可行性。

首版單筆班次長度需大於 0 且不超過 24 小時。跨日須明確給定結束日期或 end_day_offset，不依「結束小於開始」自動猜測。

週起始日預設星期一，且保存於專案。每日及每週時數按實際落在各日／各週的時間切分。最多連續日數以「當地日期內存在大於零分鐘勤務」計為一個工作日，因此夜班可能涵蓋兩個日期；介面須說明此計數方式。

跨月的完整週及連續日數，須參照同一專案中已知的鄰接日期資料，而不是在畫面邊界歸零。若所需前期／後期資料未知，顯示檢查範圍不足，不能宣稱全域或跨專案檢查完成。使用者可明確確認某個相鄰日期範圍沒有其他班次，該確認與範圍保存於 Settings；空白資料本身不等同已確認無班。未啟用的限制不要求額外邊界資料。

### 9.5 需求覆蓋

對每筆需求，依需求與指派的起訖邊界切成實際時間片段，計算每段的有效覆蓋人數。只有與該需求明確關聯、職務／場地相符且該區段未違反硬限制的指派可以計入。同一人每段最多計一次。

缺額人時 = 各時間片段 max(需求人數 − 有效覆蓋人數, 0) × 片段時數的總和。

需求覆蓋率 = 1 − 缺額人時 ÷ 總需求人時。超額配置不能抵銷其他時段的缺額；同時另外顯示超額人時。沒有需求時顯示「未設定需求／不適用」，不能顯示 100%。

例如需求為 09:00–13:00 兩人，甲排 09:00–13:00，乙排 09:00–12:00：12:00–13:00 仍缺一人，缺額為一人時；不能因為有兩張卡片就判斷已滿編。

### 9.6 檢查與匯出狀態

可隨時匯出完整專案及草稿班表。存在硬衝突、人力缺口或必要跨期資料不足時，閱讀版需標示草稿及原因，不能標成「需求已滿且檢查完成」。

純手動且沒有需求的專案可顯示「已檢查已知指派限制，需求覆蓋未評估」。任何影響班表的修改都使先前檢查結果失效，匯出前必須按目前版本重新檢查。

## 10. 本機輔助排班

### 10.1 定位

首版是規則式排班助手，不需要 AI API 或後端。輸出是一個可解釋、可人工修正的草稿；不承諾全域最佳解，也不把「本次搜尋沒有找到」說成數學上無解。

### 10.2 輸入

專案快照、人員與資格、可排／不可排／偏好時段、人力需求、已排班次、鎖定狀態、已啟用限制、目標權重及演算法設定。

若沒有需求，介面應引導建立需求，不根據人員名單自行猜測每日需要幾個人。

### 10.3 兩種模式

**只補空缺（預設）：** 所有既有班次都當作固定輸入，無論是否鎖定；只新增合格指派。

**重新安排未鎖定班次：** 先顯示可能移除及調整的範圍；保留鎖定班次，其餘可重排。人工建立的未鎖定班次也可能受影響，須明確提示，不可只用模糊的「重新最佳化」按鈕。

### 10.4 求解策略

先處理候選人較少的需求，再以已知安排扣除需求，形成連續缺額區段。優先尋找能完整覆蓋該區段的合格人員，依偏好與負載排序，必要時進行有界限的交換或重試。

首版不自動為了硬湊覆蓋而切出大量極短班次。若某段缺額無人可完整覆蓋，可顯示可部分支援的人員與時段，讓使用者手動拆分；進階自動拆班留待後續。

有設定目標工時者，以目標達成程度作為負載參考；未設定者，以本次規劃區間可排時間與既有負載作為參考。演算法不得只依員工名單順序重複偏袒前幾人。具體權重與比較順序在演算法設計文件中版本化，測試需包含異質可排條件。

### 10.5 結果與解釋

結果須區分：需求全數覆蓋、產生部分可行班表、輸入硬衝突、計算被取消、到達搜尋預算及計算錯誤。

顯示新增／修改／移除班次數、缺額時段、人員負載與未排原因。原因可以是可排時段不足、缺少職務資格、已達設定上限、受已鎖定班影響，或本次計算預算內尚未找到安排。不能將局部候選人排除原因誇大成全局無解證明。

套用前呈現差異；套用為一筆可撤銷交易。若計算期間專案版本變更，結果失效，必須重新計算，不可覆寫新資料。

### 10.6 計算執行

將排班計算放在 Web Worker，讓介面能繼續顯示進度及接收取消；Web Worker 可在不同於介面執行緒的環境執行工作。[S4]

保存 algorithm_version、seed、搜尋次數上限與來源專案版本。相同演算法版本、標準化輸入、設定、種子及迭代上限，且未因中斷／時間保護停止時，需得到一致結果。時間保護提前中止的結果須另行標記，不承諾與完整搜尋完全相同。

## 11. 本機保存、資料安全與隱私

### 11.1 儲存策略

以 IndexedDB 保存專案及恢復快照，localStorage 僅存輕量介面設定。畫面顯示「儲存中」「已儲存在此瀏覽器」「儲存失敗」，成功狀態只能在實際提交完成後顯示。[S3]

本機儲存不等於備份。瀏覽器清除資料、私密瀏覽結束或儲存回收，都可能導致資料不再存在；持續性儲存請求也不能取代使用者自行備份。[S3]

提供明顯的「匯出專案備份」入口，在匯入取代、刪除或大量變更前提醒。持續性儲存可以在合適時機請求，但不可宣稱永久不會丟失。

### 11.2 交易及多分頁

成功編輯以交易提交。重大操作前保留最多五份恢復快照，至少保留最近一次成功狀態；當前工作階段提供最多一百筆 Undo／Redo 操作，不承諾關閉瀏覽器後保留全部操作歷史。

同一專案同時開在多個分頁，首版僅允許一個寫入者，其餘分頁呈現唯讀或明確接管提示。寫入時檢查專案版本，避免最後寫入者無聲覆蓋。多分頁防護不是多人共編。

### 11.3 資料最小化

不要求身分證、銀行帳戶、薪資、電話、住址或請假原因。可排資料只需時間與狀態。閱讀版匯出預設排除可排限制及內部備註。

不接第三方分析、雲端 AI、廣告或會讀取班表的外部服務；資源及字型盡量隨應用提供。開源示範僅用虛構人員，錯誤紀錄及截圖不得內含真實名單。

網站主機仍可能記錄一般連線資訊；「不傳送排班內容」不等於「沒有任何網路連線」或「主機完全沒有日誌」。共用電腦上的本機資料也不具使用者登入隔離，需提供清除資料操作及明確說明。

### 11.4 檔案與內容安全

匯入資料皆視為不可信輸入。禁止執行巨集、公式及 HTML；不追蹤匯入的外部連結。對壓縮檔、解壓後資料量、列數、儲存格數與字串長度設定限制，超限時需能取消並安全退出，而不是只檢查副檔名。

初始限制目標為 .xlsx 壓縮後不超過 10 MiB、總資料列不超過 20,000、非空儲存格不超過 300,000、單一文字欄位不超過 2,000 字元。解壓資料量保護須在解析實驗中落實，不可將這些數字視為已證明足以防護所有惡意檔案。

## 12. 時區與日期支援界線

專案保存時區，不依使用者電腦時區改寫既有班次。首版以固定 UTC+08:00、標籤 Asia/Taipei 為正式支援範圍；英文版、其他固定時區或夏令時間地區不列為首版已支援。

日期使用西元、時間採 24 小時制。不把只有日期的值經過隱性 UTC 轉換而偏移一天。不支援的專案時區須阻擋編輯／匯入，不得假裝轉換成功。此範圍是為控制首版複雜度的產品決策，不是靜態網站的技術限制。

## 13. 技術方向與開源要求

### 13.1 建議架構

採單一 Repository 的 React＋TypeScript＋Vite 前端專案；排班引擎、時間與規則、Excel 資料轉換及介面分開。這是技術建議，尚非經過實驗後定案的技術選型。

GitHub Pages 是靜態託管服務；Vite 亦提供靜態產物及 GitHub Pages 的部署方式。因此，網站託管本身不需要額外的應用後端。[S1]

「靜態部署」指沒有執行中的應用伺服器；Excel 解析、排班運算及編輯仍在瀏覽器執行。首次開啟通常需要載入網站資源；關閉後離線重開屬 PWA 第二階段，不應在首版宣稱自動具備。

| 取消 | 使用者發出取消後 1 秒內顯示已取消，且不修改既有班表 |
| Excel 往返 | 核心資料一致性測試全數通過 |
| 桌面瀏覽器 | 發布時最近兩個主要版本 Chrome、Edge、Firefox 的指定測試組合 |
| Safari／手機 | 先驗證可用性；只有完成測試的功能才列入正式支援 |
| 無障礙 | 核心流程可只用鍵盤及不拖拉的點選方式完成，錯誤有可讀文字 |
| 隱私 | 核心流程網路檢查中不出現名單、規則或班表內容的外傳 |

效能門檻不能成為刪除資料、跳過規則或無聲截斷匯入的理由。超限需說明並保留原專案。

## 15. 核心驗收案例

| ID | 情境 | 預期結果 |
| --- | --- | --- |
| AC-01 | 匯入 0012 與 0013，姓名相同 | 建立兩名不同人員，前導零保留 |
| AC-02 | 同一含穩定 ID 專案檔重複匯入 | 不產生重複資料；取代與另開專案行為明確 |
| AC-03 | 某人僅週一 09:00–17:00 可排，週一 13:00–15:00 不可排 | 不得安排跨越不可排區段的完整班次 |
| AC-04 | restricted 人員沒有時段 | 不加入自動排班，顯示原因與設定入口 |
| AC-05 | 09:00–12:00 和 12:00–15:00 | 不判定時間重疊；每日與每週時數依實際時間正確累計 |
| AC-06 | 夜班 22:00–翌日 06:00，翌日另排重疊班 | 正確辨識重疊，跨日工時只計一次並分攤日期 |
| AC-07 | 拖拉班次到不可排人員 | 顯示原因、還原原位置，資料版本不發生錯誤提交 |
| AC-08 | 鎖定後重新安排其他班次 | 鎖定指派的 ID、人員、日期及時間完全不變 |
| AC-09 | 只有一名合格人員，需求兩人 | 保留缺額，不安排不合格者，不假稱需求已滿 |
| AC-10 | 需求四小時兩人，其中一人只排三小時 | 最後一小時顯示缺一人，缺額一人時 |
| AC-11 | 匯入到一半發現無效人員關聯 | 整次匯入不提交，原專案保持不變 |
| AC-12 | 專案匯出後在乾淨工作區匯入 | 核心資料、規則、鎖定及關聯標準化後一致 |
| AC-13 | 匯出含衝突或缺額的班表 | 可以輸出，但明確標記草稿與原因 |
| AC-14 | 調整與自動排班後 Undo／Redo | 每次還原整筆操作，需求與工時統計同步更新 |
| AC-15 | 計算中使用者修改人員資料 | 舊計算結果失效，不得覆蓋較新版本 |
| AC-16 | 儲存配額不足或儲存交易失敗 | 不顯示已保存，保留記憶體資料並提供立即匯出 |
| AC-17 | 同專案開兩個分頁編輯 | 第二寫入者被阻擋或需明確接管；沒有靜默覆蓋 |
| AC-18 | 班表月份只涵蓋一個日曆週的一部分 | 使用可得的相鄰資料檢查；資料不足時明確警告 |
| AC-19 | 修改規則使鎖定班次違規 | 保留待處理草稿，自動排班停止並說明，不略過違規 |
| AC-20 | 透過點選及鍵盤、不使用拖拉 | 可完成人員改派、日期與時間調整、複製及刪除 |
| AC-21 | 非 30 分鐘格的 09:20 指派往返 Excel | 保持原始分鐘，不自行四捨五入 |
| AC-22 | 匯入公式、錯誤 schema 或超限檔案 | 顯示具體原因並安全停止，不執行內容或破壞專案 |
| AC-23 | 複製範本或班次到新日期 | 產生新 ID，重新驗證時段、跨期限制及需求關聯 |
| AC-24 | 核心操作期間檢查網路請求 | 無排班資料傳輸；只允許說明中列出的靜態資源請求 |

## 16. 開發里程碑與發布門檻

| 階段 | 交付內容 | 階段通過標準 |
| --- | --- | --- |
| M0：資料與可行性 | Excel 契約、時間與需求模型、虛構測試資料、Excel 瀏覽器解析及時軸互動實驗 | 跨日、ID、schema、時間語意及依賴授權可驗證；重要風險有處置 |
| M1：最小往返閉環 | 建專案、名單匯入、表單式手動排班、專案及閱讀版匯出、再次匯入 | 尚無自動排班也能完成一份可恢復的班表 |
| M2：視覺化與檢查 | 週表、單日時軸、拖拉與長度調整、可排時段、需求覆蓋、Undo／Redo | 編輯語意一致；跨日與缺額驗收通過 |
| M3：輔助排班 | 本機引擎、兩種模式、鎖定、預覽、取消、缺額解釋與統計 | 不產生違規指派、不覆寫固定資料，失敗與部分結果可辨識 |
| M4：公開 MVP | 儲存安全、多分頁、檔案防護、瀏覽器相容、說明、範本、授權、公開部署 | 核心驗收全數通過、無已知資料遺失問題、文件與功能一致 |

M1 是可驗證的第一個切片，不是把自動排班移出原本承諾的 MVP。正式 MVP 包含 M1–M4 的核心能力。日期及工期需在開發者實際估算與技術實驗後安排，本文件不預設完成時程。

## 17. 成功指標與驗證方式

第一輪招募至少五名實際有排班工作的人，使用各自去識別化的既有情境進行測試。事先記錄用原本方式完成相同任務的時間，並比較 RosterLeaf 的完成時間、錯誤及主觀負擔。

提案目標：示範專案首次上手在三分鐘內完成主要流程；已備妥標準資料者的同等排班任務時間中位數降低至少 50%；使用者能分辨專案備份與閱讀版；關閉後或換工作區能成功恢復資料。

這些是待驗證目標，不能在 README 宣稱為已達成的市場實績。產品預設不蒐集使用者班表或行為分析；研究透過明確同意的測試及回饋完成。

## 18. 主要風險與處置

| 風險 | 處置 |
| --- | --- |
| 任意 Excel 格式導致 scope 失控 | 首版固定資料契約＋一般名單欄位對應，不承諾自動解析所有班表 |
| 自動排班被誤解成必定能排滿 | 顯示需求、限制、缺額與搜尋狀態，不誇稱最佳或無解 |
| 本機資料被清除 | 清楚的儲存狀態、匯出專案、恢復快照與資料持續性提示 |
| 拖拉與捲動互相干擾 | 分開週表與日時軸操作、點選替代方式、觸控回歸測試 |
| 手動調整造成假的滿編 | 以真實時間區段計算需求覆蓋，而不是計卡片數 |
| UI 套件授權不符合開源 | M0 先核對實際插件和依賴，不等完成後才檢查 |
| 混淆排定時數與法定工時／薪資 | 說明計算口徑，不提供未驗證的合規或薪資認證 |
| 沒有跨期資料仍宣稱檢查完整 | 顯示資料範圍、外部未知資料與邊界警示 |
| 檔案交接產生多份版本 | 保存專案 ID、內容版本與匯出時間，不提供隱性自動合併 |
| 開源示範洩漏真實個資 | 虛構 fixtures、匯出最小化、Issue 與截圖去識別化指引 |
